# Sensitivity sweep results

Generated by `uv run python scripts/run_sensitivity_sweep.py` and
`uv run python scripts/run_alert_timeline.py`. Committed
rather than regenerated on demand: the corpus is seeded, so an unchanged
codebase reproduces these files exactly, and a diff here means a detector
changed behaviour. See [../docs/SENSITIVITY_ANALYSIS.md](../docs/SENSITIVITY_ANALYSIS.md)
for the method and [../docs/DETECTION_TUNING.md](../docs/DETECTION_TUNING.md)
for what the numbers mean.

## `sweep_metrics.csv`

One row per grid point — a detector, a threshold, an evaluation window.

| Column | Meaning |
|---|---|
| `detector` | Detector class name, as in `config/detectors.json`. |
| `parameter` | The configuration field being swept. |
| `threshold` | Its value at this grid point. |
| `window_seconds` | Seconds of capture time between `evaluate()` calls. |
| `true_positives` … `true_negatives` | Case counts over the 49-case corpus. |
| `precision`, `recall`, `false_positive_rate`, `f1` | Derived rates. |

**An empty rate cell means undefined, not zero.** Precision is empty when the
detector never fired: it made no claim to be right or wrong about. Reading
that as 0.0 would put a silent detector next to one that alerted constantly
and was always wrong.

## `case_outcomes.csv`

One row per (detector, window, case) — the per-case detail behind the
aggregates above.

| Column | Meaning |
|---|---|
| `expected` | 1 if this case is labelled for this detector. |
| `highest_firing_threshold` | The largest swept threshold at which the detector still fired on this case; empty if it never fired. |

Firing is monotone in the threshold, so this single number reproduces the
whole row: the detector fires at any threshold at or below it. The sweep
checks that monotonicity on every case rather than assuming it.

This is the file to read when a rate looks wrong. An aggregate says a detector
lost recall; this says which case it started missing and how far the threshold
had to move.

## `alert_timeline.csv`

One row per alert raised over a composed half-hour of traffic — benign
background throughout, five attacks placed inside it — replayed twice: at the
configuration that ships, and at the one the sweep recommends. Same packets
both times, so the difference is the configuration and nothing else.

| Column | Meaning |
|---|---|
| `config` | Which configuration raised it. |
| `raised_at` | Seconds into the capture at which the evaluation that emitted it ran. Not the packet time: an alert does not exist until the evaluation that emits it, however long ago the traffic arrived. |
| `detector` | The detector that raised it. |
| `attributable` | 1 if an attack this detector is responsible for was running inside the window that produced the alert. |

The two files answer different questions and will disagree in tone. The sweep
is measured case by case in isolation, which is what makes precision and recall
well-defined; this is what an analyst's console would have shown. The corpus is
half attacks and a real segment is not, so a false-positive rate that looks
small in `sweep_metrics.csv` becomes a steady stream of alerts here.
